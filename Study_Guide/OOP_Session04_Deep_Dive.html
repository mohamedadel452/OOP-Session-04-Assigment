1) Abstraction

الفكرة: بتستخدم الشيء من غير ما تعرف هو شغال إزاي. زراير العربية هي الـ abstraction، والمحرك هو التنفيذ المخفي.

الفكرة التقنية: تكتب كودك بالاعتماد على عقد (Contract) مش على تنفيذ، فتغيير التنفيذ ما يكسرش اللي بيستخدمه.

تصحيح (سلايد 4): السلايد بيقول إن الـ abstraction "بيعزز الأمان". ده خلط. الـ abstraction هدفه إدارة التعقيد والتغيير. أي حد معاه الـ DLL يشوف كل حاجة بـ Reflection أو ILSpy.

2) Abstract Class

public abstract class Shape
{
    public string Name { get; }
    protected Shape(string name) => Name = name;   // constructor مسموح

    public abstract double Area();                 // بدون body: الابن لازم ينفذه

    public void Describe()                         // كود جاهز
        => Console.WriteLine($"{Name}: {Area():F2}");
}

public class Circle : Shape
{
    private readonly double _r;
    public Circle(double r) : base("Circle") => _r = r;
    public override double Area() => Math.PI * _r * _r;   // override إجبارية
}

// new Shape("x");        // CS0144: مينفعش instance
Shape s = new Circle(5);  // reference من الأب، object من الابن
s.Describe();             // Circle: 78.54

ليه مينفعش new Shape()؟

لأن Area() ملهاش جسم. لو اتعمل object ونادينا عليها، مفيش كود يتنفذ. فالـ Compiler بيمنع الحالة من الأصل.

الميكانيزم: الـ Method Table (vtable)

  • كل class فيه دوال virtual/abstract/override له Method Table فيه slots، وكل slot بيشاور على كود.
  • لما تنادي s.Area() الـ Runtime بيبص على النوع الفعلي للـ object مش نوع الـ reference، ويروح للـ slot ده.
  • ده الـ Runtime Polymorphism. الـ abstract method هو slot فاضي في الأب، والابن بيملاه.
  • الـ override هو اللي بيقول "أنا بحط كودي في نفس الـ slot". من غيره الـ Compiler يعتبر الـ abstract method ما اتنفذتش (سلايد 36 سؤال 8).

باگ حقيقي: استدعاء abstract/virtual من الـ Constructor

abstract class Base {
    protected Base() { Init(); }
    protected abstract void Init();
}
class Derived : Base {
    private string _name;
    public Derived() { _name = "Ahmed"; }   // بيتنفذ بعد constructor الأب
    protected override void Init() => Console.WriteLine(_name ?? "NULL!");
}
new Derived();   // NULL!

الـ virtual dispatch شغال من أول لحظة، فـ Init() بتتنفذ في Derived قبل جسم الـ constructor بتاعه. ملحوظة: في C# الـ field initializers (= "Ahmed" على الحقل) بتتنفذ قبل constructor الأب، لكن التعيين جوه جسم الـ constructor لأ. القاعدة: ماتناديش virtual من constructor.

3) Interface

public interface IPayment { void Pay(decimal amount); }

public class CreditCardPayment : IPayment {
    public void Pay(decimal amount) => Console.WriteLine($"Paid {amount} by Card");
}
public class PayPalPayment : IPayment {
    public void Pay(decimal amount) => Console.WriteLine($"Paid {amount} by PayPal");
}

static void Process(IPayment p, decimal amount) => p.Pay(amount);  // مايعرفش النوع الحقيقي
Process(new PayPalPayment(), 200);

ليه multiple interfaces مسموحة و multiple classes لأ؟

المشكلة في الوراثة المتعددة من classes هي الـ state. لو D وارث من B و C وهما وارثين من A، هل في نسخة واحدة من حقول A ولا اتنين؟ ده بيعقّد layout الـ object وترتيب الـ constructors (Diamond). الـ interface مفيهوش instance fields فمفيش state يتضارب.

تصحيح (سلايد 11 و 32): "no body / no private" كان صح قبل C# 8. دلوقتي الـ interface ممكن يحتوي default methods و static members و private helpers. بس instance fields لسه لأ.

مفهوم خاطئ: "تنفيذ الـ interface دايماً virtual"

interface IShape { void Draw(); }
class Circle : IShape { public void Draw() => Console.WriteLine("Circle"); }
class Ring : Circle   { public new void Draw() => Console.WriteLine("Ring"); }

IShape s = new Ring();
s.Draw();   // Circle !

الـ implicit implementation بيتعلّم في الـ IL كـ virtual final. الـ interface map بتاع Circle بيشاور على دالته، و Ring ما عملش re-implementation. الحل: خلي Draw virtual وسوّي override، أو اكتب class Ring : Circle, IShape.

ليه ده مهم للـ Backend؟ (DI)

builder.Services.AddScoped<IPaymentService, PayPalPayment>();
public class OrderController(IPaymentService payment) { }

الـ DI والـ unit testing بالـ mocks معتمدين على إنك تطلب IPaymentService في الـ constructor. من غير الـ interface كل class مربوطة بتنفيذ واحد.

باگ أداء ومنطق: Struct + Interface = Boxing

interface ICounter { void Inc(); int Value { get; } }
struct Counter : ICounter { int _v; public void Inc() => _v++; public int Value => _v; }

var c = new Counter();
ICounter i = c;      // boxing: نسخة على الـ Heap
i.Inc();
Console.WriteLine(c.Value);   // 0 : الأصلي ما اتغيرش

لتجنب الـ boxing استخدم generic بقيد: void Run<T>(T x) where T : ICounter. الـ JIT بيولّد كود متخصص لكل struct.

4) الموضوعات المتقدمة في الـ Interface

4.1 تعارض الأسماء

interface IFirst  { void Display(); }
interface ISecond { void Display(); }
class MyClass : IFirst, ISecond {
    public void Display() => Console.WriteLine("MyClass.Display()");  // تنفيذ واحد للاتنين
}

4.2 Explicit Implementation

interface ILogger    { void Log(string m); }
interface IAuditable { void Log(string m); }

class FileLogger : ILogger, IAuditable {
    void ILogger.Log(string m)    => Console.WriteLine($"[LOG] {m}");
    void IAuditable.Log(string m) => Console.WriteLine($"[AUDIT] {m}");
}

var f = new FileLogger();
// f.Log("x");                 // لا تظهر على النوع
((ILogger)f).Log("started");   // [LOG] started
((IAuditable)f).Log("login");  // [AUDIT] login
  • مالهاش access modifier، ومش بتظهر إلا من reference بنوع الـ interface.
  • استخدام فعلي في الـ BCL: List<T> بينفذ IList (غير generic) explicitly عشان يخبي Add(object) غير الآمنة.
  • الثمن: مع الـ struct أي استدعاء عن طريق الـ interface بيعمل boxing.

4.3 Default Interface Methods (C# 8+)

public interface IPrinter {
    void Print(string text);
    void PrintLine(string text) => Print(text + "\n");   // default
}
class ConsolePrinter : IPrinter {
    public void Print(string text) => Console.Write(text);
}

var cp = new ConsolePrinter();
// cp.PrintLine("x");     // CS1061
IPrinter p = cp;
p.PrintLine("World");     // يشتغل

تصحيح (سلايد 24): التعليق "PrintLine is inherited" غلط. الـ default method مش بتتوّرث ومش بتظهر على نوع الـ class، بس عن طريق reference من نوع الـ interface. وده سبب إن سلايد 27 اشتغل: كتب IGreet g = new Person();.

ليه اتصممت كده؟ الهدف تطوير interface منشور من غير ما تكسر اللي بينفذوه. قبل C# 8 إضافة دالة لـ interface كانت بتكسر كل class بينفذه.

Diamond مع الـ Default Methods

interface IA { void M() => Console.WriteLine("IA"); }
interface IB : IA { void IA.M() => Console.WriteLine("IB"); }
interface IC : IA { void IA.M() => Console.WriteLine("IC"); }
class D : IB, IC { }   // CS8705: no most specific implementation

الـ Compiler بيرفض الغموض. الحل override صريح في D.

5) المقارنة: Abstract Class مقابل Interface

البندAbstract ClassInterface
الفكرةis-a مع كود مشتركcan-do: قدرة
State (fields)نعملا (static فقط)
Constructorنعملا
كود جاهزنعممحدود (default methods)
عدد ما تورثهواحدأي عدد
إضافة member لاحقاًvirtual آمن، abstract يكسرآمن لو default
مع الـ structلانعم (مع boxing)

متى؟ Abstract class لما في state وسلوك مشترك بين أنواع متقاربة (مثال: Document و PdfDocument). Interface لأنواع مالهاش علاقة بتشترك في قدرة (مثال: Invoice و Image كلهم IExportable). والنمط الشائع هو الاتنين مع بعض: abstract class RepositoryBase<T> : IRepository<T>.

الحدود: الـ abstract class بتحبسك في شجرة وراثة واحدة، والـ hierarchy العميقة بتعمل Fragile Base Class (تعديل في الأب يكسر الأبناء). والـ interface لكل class بتنفيذ واحد بيزود التعقيد من غير فايدة، استخدمه لما يكون في أكتر من تنفيذ أو احتياج للـ mocking.

7) ملاحظة سينيور

في C# 11 ظهرت static abstract members في الـ interface وهي أساس الـ Generic Math (INumber<T>)، فتكتب T Add<T>(T a, T b) where T : INumber<T> وتشتغل على int و double من غير boxing.
